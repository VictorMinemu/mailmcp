# Languages

MailMCP includes English (`en`) and Spanish (`es`) for the web client and application-owned MCP text. Account labels, sender names, folder names, email content, attachment filenames and attachment bytes are never translated. Protocol identifiers, tool names, input field names and error codes remain stable.

## Web client

Language selection follows this order:

1. A supported `?lang=` query parameter, including links generated by `web_open`.
2. The user's saved choice in `localStorage` (`mailmcp.language`). No credentials or mail data are stored there.
3. The browser's preferred languages; regional tags such as `es-CO` and `en-GB` match their base language.
4. English fallback.

The language selector is available on the main page and inside account/compose dialogs. Switching updates labels, placeholders, accessibility labels, application errors, validation feedback, dates and attachment actions without resetting forms or re-fetching mail. Native browser chrome, such as the file-save dialog, follows the browser's own language setting. If browser storage is disabled, language selection still works for the current page. If loading a catalog fails, the active language is retained and an error is shown.

The page updates its HTML `lang` attribute and title. The initial HTML fallback is English before JavaScript loads the chosen catalog. Requests send the chosen `Accept-Language`, and API errors include a localized `message` plus stable `code` and `messageKey` fields. The login token remains in the fragment until removed by the app; language selection does not expose it in query parameters or persist it.

## MCP

For local stdio, set `MAILMCP_LANGUAGE=es` (default `en`) in the server environment. Restart that process to change its descriptions and prompts.

For hosted HTTP MCP, send `Accept-Language: es` on requests. The server honors quality weights and supported regional language tags and falls back to `MAILMCP_LANGUAGE`. Language is chosen per request, never through shared mutable server state. Use a consistent header for a client's requests so its tool catalog and later results use the same language.

This translates tool descriptions, server instructions, the account resource description, the reply-drafting prompt and application error messages. MCP/SDK protocol-level diagnostics are managed by the SDK. Machine-readable JSON data and schemas are not renamed.

`web_open` accepts an optional `language` argument:

```json
{ "language": "es" }
```

The returned link selects that web language. If omitted, it uses the MCP request/process language. Authentication and owner isolation are independent of language.

## Adding a language

Catalogs live in `locales/en.json` and `locales/es.json`, with `web`, `mcp` and `errors` sections. Web and server use these same files. Translate every key and preserve interpolation placeholders such as `{filename}`. Error lookup keys use the canonical English application message and must stay unchanged. Translations are rendered as text, never HTML.

Add the language to the catalog loader in `src/i18n.ts`, the supported list and types in `web/language.js` and `web/language.d.ts`, the explicit catalog route in `src/web.ts`, the `web_open` enum and capabilities in `src/mcp.ts`, and the native-name selector options in `web/index.html`. Keep catalog routes restricted to supported languages. Update catalog-parity tests in `tests/i18n.test.ts` and browser checks for the new language. Right-to-left layout needs a separate `dir` and layout update; the two initial languages are left-to-right.

Run `npm run format:check` and `npm run check`. Tests check catalog completeness, interpolation parity, language negotiation, translated MCP and HTTP results, and preservation of user data.
